问题 3：执行器启动开销

“In a number of workloads involving simple queries we currently spend most of the time within ExecInitNode().”

是什么
简单查询（取一两行的 OLTP 语句）每次执行都要先建一整棵执行状态树，执行完再拆掉。真正取数据的时间反而不多。
原因
① 本该在规划阶段做一次的推导（例如由目标列建 TupleDesc、聚合节点查系统表）每次执行都重做；② 初始化时做大量细小的 palloc。
思路
把推导挪到规划期；初始化前先算出总内存、一次分配到位（第 6 步）。退一步的做法：按计划复杂度设定 es_query_cxt 的块大小，或提供“不单独释放”的分配接口。
难点
权限、锁、参数相关的工作必须留在执行期；精确算出内存要扫两遍，扩展还会自行分配；改分配器牵涉面广；新增的簿记会拖慢用不上它的语句；先得有剖析数据。
现状
第 6 步没有实现。es_query_cxt 仍用默认块大小，表达式步骤数组仍从 16 个开始翻倍。

问题 5：执行时的内存开销

“It'd be far better if we could share a lot of state between successive executions of the same prepared statement.”

是什么
同一条 prepared statement 反复执行时，计划是复用的，但执行状态（PlanState、ExprState 等）每次从零建、用完即删，几次执行之间不共享任何东西。
思路
把状态拆成“不可修改”和“可修改”两部分。可修改部分只用偏移量引用，每次执行复制一份；不可修改部分共享（第 7 步）。
难点
同一计划可能被递归或交错地同时执行，可修改部分不能共享；执行器里到处是绝对指针，改成偏移量侵入性极大、代码难读；有些值在“编译”时还不知道；buffer pin、打开的关系这类外部资源没法靠复制得到。
现状
只在表达式层做过原型（2019 年 31 个补丁，2020 年退回，2021、2023 年两次重整分支），没有合入；拆出来的几个独立优化已经合入。JIT 生成的代码至今不能缓存。

两个问题的根源相同：执行状态每次执行建一份，放在一个随执行删除的内存上下文里，不可变内容和可变内容混放，彼此用绝对指针相连。Andres 对两者开的是同一张方子，即一次分配加偏移量引用：第 6 步解决分配问题，第 7 步解决共享问题。详见两个问题的关系。

背景知识

这一部分按初级内核工程师的起点来写。每节开头说明它为什么和问题 3、问题 5 有关。

B1　Plan、PlanState、Expr、ExprState 和 EState

为什么要懂：问题 3 和问题 5 讨论的都是“执行状态”。先要分清哪些结构属于计划（可以缓存），哪些属于执行状态（每次执行新建）。

一条 SQL 在后端依次经过解析、语义分析与重写、规划、执行。规划器的输出是 PlannedStmt，其中最主要的是一棵 Plan 树，比如 IndexScan 上面接 Agg。执行器拿到 Plan 树后，并不直接在它上面运行，而是先建一棵形状相同的 PlanState 树。执行器 README 是这样说的：

译文规划器交付的计划树由 Plan 节点组成（各种由 struct Plan 派生的结构体类型）。执行器启动时，我们会建一棵结构完全相同的平行树，里面是执行器状态节点。一般来说，每种计划节点类型都有对应的执行器状态节点类型。状态树中的每个节点都有一个指针指向计划树中的对应节点，再加上实现该节点类型所需的执行器状态数据。这样安排以后，对执行器来说计划树可以是完全只读的：执行期间会被修改的数据全部在状态树里。只读的计划树让计划缓存和复用简单得多。

表达式也是同样的两层结构。计划里的条件、目标列是 Expr 树（只读）；执行器为每棵 Expr 树建一个 ExprState，里面是编译好的求值步骤（见 B4）。整条查询还有一个 EState，存放查询级的执行状态：范围表、快照、参数、结果关系、元组表，以及最重要的每查询内存上下文 es_query_cxt。QueryDesc 把 PlannedStmt、EState 和 PlanState 根节点捆在一起，交给执行器的各个入口函数。

解读

记住一句话：计划只读、可以缓存；执行状态每次新建。这个设计让计划缓存变得简单，代价是每次执行都要重新建、重新拆执行状态。问题 3 关注的是这个代价的 CPU 部分，问题 5 关注的是它的内存部分和不能共享这一点。

B2　执行器的四个阶段

为什么要懂：问题 3 说的“启动开销”就是 ExecutorStart 这一段；问题 5 说的“每次从头初始化”指的是每次执行都完整走一遍这四个阶段。

  • ExecutorStart（execMain.c:140）：CreateExecutorState() 新建 EState 和每查询内存上下文（:174），然后 InitPlan()（:260、定义在 :826）检查权限（:841）、建范围表、打开结果关系，再调 ExecInitNode()（:959）沿 Plan 树递归，为每个节点建对应的 PlanState。
  • ExecutorRun：反复调用根节点的 ExecProcNode()。每次调用，节点向子节点要一行（再由子节点向它的子节点要），加工后返回一行。这叫拉取式或 Volcano 式执行。节点第一次被调用时先经过 ExecProcNodeFirst()（execProcnode.c:443），它检查栈深度，并在需要时换上带插桩的入口。还有一些初始化工作推迟到第一次取行时才做，例如索引扫描在 IndexNext() 里才调用 index_beginscan()（nodeIndexscan.c:109）。
  • ExecutorFinish：跑完尚未结束的 ModifyTable 节点，执行 AFTER 触发器（外键检查也在这里）。
  • ExecutorEnd（execMain.c:469）：ExecEndPlan()（:494）递归关闭关系、释放 buffer pin 等资源；FreeExecutorState()（:509）删除整个每查询内存上下文，PlanState 树、ExprState 等随之全部释放。

所谓简单查询，是计划只有一到几个节点、只处理几行的语句，例如按主键取一行、插入一行、按主键更新一行。这类语句的 ExecutorRun 很短；ExecutorStart 和 ExecutorEnd 要做的事却基本固定，跟处理行数无关，所以相对很重。

B5　内存上下文、palloc 和“小块分配”

为什么要懂：问题 3 的第二个原因是“大量细小的分配”；2023 年的讨论全部围绕执行器的内存上下文展开。

B6　Prepared statement 与计划缓存

为什么要懂：问题 5 的原话就是“同一个 prepared statement 的连续多次执行”。要先弄清 prepared statement 复用了什么、没复用什么。

客户端可以用 SQL 的 PREPARE/EXECUTE，或者扩展查询协议的 Parse/Bind/Execute 消息来使用 prepared statement。服务端为它保存一个 CachedPlanSource（分析、重写过的查询），并按需生成 CachedPlan（规划好的计划）。每次执行时由 GetCachedPlan()（plancache.c:1168）决定用定制计划还是通用计划（choose_custom_plan()，:1046）：

译文先生成定制计划，直到至少做过 5 次（这个数是随意定的）。之后算出定制计划的平均代价：如果通用计划比它便宜，就优先用通用计划。（因为定制计划的代价里计入了规划本身的代价，这意味着通用计划只需比“定制计划的执行代价加重新规划代价”便宜即可。）注意，如果 generic_cost 是 -1（表示还没算出通用计划的代价），此时总是优先用通用计划。

  • 定制计划（custom plan）：每次用实际参数值重新规划；
  • 通用计划（generic plan）：参数当作未知数规划一次，以后每次执行都用这一份。参数 plan_cache_mode 可以强制选其中一种。

以扩展协议为例，Bind 消息由 exec_bind_message()（postgres.c:1631）处理：取计划（:2024），建 Portal 并 PortalStart()（:2046）。对 SELECT（PORTAL_ONE_SELECT 策略，pquery.c:474），PortalStart 里 CreateQueryDesc()（:495）后调用 ExecutorStart()（:517），Execute 消息由 exec_execute_message()（postgres.c:2102）跑 PortalRun 取行，Portal 关闭时调用 ExecutorEnd。不带 RETURNING 的 INSERT、UPDATE、DELETE 则在 PortalRun 里经 ProcessQuery()（pquery.c:136）一次走完 Start、Run、Finish、End。

解读

所以用通用计划时，省掉的是规划，省不掉的是执行器的启动和收尾：每次 EXECUTE 仍然完整地建一次、拆一次 EState、PlanState 和 ExprState。这正是问题 5 的场景。

prepared statement 的“内存开销”有两种，读后面的讨论时要分清：一种是每次执行在 es_query_cxt 里反复分配、释放的内存；另一种是常驻的，即缓存的计划本身，每个后端、每条语句各占一份。2019 年的 BUG #15923 说的是后一种。

B7　绝对指针、相对指针和“克隆一块内存”

为什么要懂：Andres 的方子是“可写内存用偏移量引用，而不是指针，这样就能克隆”。要理解为什么非用偏移量不可。

C 语言的指针存的是绝对地址。假设一块内存里，对象 A 有一个指针指向同一块内存里的对象 B。把整块内存 memcpy 到新地址以后，新的 A 里存的仍然是旧 B 的地址。要让副本能用，就得逐个修正内部指针（“重定位”）；这件事既慢又容易漏。如果 A 存的是“B 相对于块首的偏移量”，复制以后偏移量照样有效，用的时候拿新块的基址加上偏移就行。

  • 代价：每次访问多一次加法。Andres 2021 年的说法是，在 x86 上基址可以一直放在寄存器里，这个开销很小。
  • PostgreSQL 里已有一套相对指针宏 utils/relptr.h，用于动态共享内存（同一段共享内存在不同进程里可能映射到不同地址）。在 17.10 中只有 freepage.c/freepage.h 用到它。
  • 同样的思路在编译器和操作系统里很常见，例如位置无关代码、x86-64 相对指令指针的寻址、重定位之前的目标文件。Andres 在 2021 年拿这些作类比。

B8　可重入：同一个计划为什么会被“同时”执行

为什么要懂：2021 年 Andres 反驳 Robert 的核心理由是“同一个表达式可能同时被求值多次，以递归的方式”。任何“把执行状态挂在计划上复用”的设计都绕不开这一点。

PostgreSQL 是单线程后端，这里的“同时”指的是一次执行还没结束，同一份计划又开始了另一次执行。常见情形有：

  • 递归调用：plpgsql 函数 f 里的一条查询调用了 f 自己。外层那次执行停在半路，内层又执行同一条（缓存在函数里的）计划。
  • 交错的游标：同一条 prepared statement 绑定出两个 Portal，客户端交替从两个 Portal 取行。
  • 嵌套调用：查询里的某个函数又去执行一条查询，而那条查询用的计划恰好是外层正在用的那份。

现在的执行器之所以没有这个问题，是因为每次执行都有自己的 EState、PlanState 和 ExprState。这也正是问题 3、问题 5 想省掉的那部分开销。

PostgreSQL 里已经有一处跨执行复用执行状态的现成做法：plpgsql 的 simple expression（像 x + 1 这样不需要完整执行器的表达式）。它在每个事务里只建一份 ExprState，然后反复使用：

译文因为对一个 simple expression 我们只保存一棵执行树，所以无法处理递归的情况。因此，如果发现这棵树在当前事务中已经在被求值，我们就直接返回 false，让调用方用常规的办法执行表达式。（其他方案，比如为递归调用新建一棵树，要么会造成内存泄漏，要么需要足够多的簿记，以至于未必划算。）expr_simple_in_use 检查还覆盖另一种情况：之前对这棵树的某次执行因为出错而中止，树里可能留有错误的状态，所以我们不敢复用它。

为什么要懂：问题 5 的后续讨论（2019、2021）很大一部分是从 JIT 缓存的角度出发的。JIT 缓存和“多次执行共享状态”卡在同一个地方。

PostgreSQL 11 起可以用 LLVM 把表达式编译成机器码（提交 2a0faed9d7，2018-03-20），元组解构也可以 JIT，由 jit_above_cost 等参数控制何时启用。代价是生成 LLVM IR、优化、生成机器码都很慢，只有对足够长的查询才划算。如果生成的代码能缓存起来下次再用，短查询也能受益。但目前做不到：

译文目前还不能缓存生成的函数，尽管从性能角度看这是很有价值的。问题在于，生成的函数通常含有指向每次执行内存的指针。需要对表达式求值机制做一些重新设计来避免这一点：基本上，所有每次执行用的内存都需要以“相对于 ExprState 中存放的一块内存的偏移量”来引用，而不是用指向内存的绝对指针。这一点解决之后，加一个以生成的 LLVM IR 为键的 LRU 缓存，就能让较快的查询也用上优化过的函数。更长期的项目是把表达式编译移到规划阶段，从而例如可以把编译好的表达式和 prepared statement 绑定。更进一步的做法是先用较少的优化做 JIT，再在后台构建优化版本。但那就更远了。

这里的“指向每次执行内存的指针”，就是 B4 中步骤里的 resvalue、fcinfo 等。JIT 把这些地址当作常量写进了代码，所以代码只对这一份 ExprState 有效。要让代码能缓存，和要让执行状态能共享，需要解决的是同一件事。

3.4　梳理

一、问题是什么

  1. 现象：简单查询的时间花在建状态树上。Andres 说，在不少由简单查询构成的负载里，大部分时间花在 ExecInitNode()。简单查询的 Run 很短，而 Start 要沿计划树逐个节点建状态，End 再逐个拆掉（B2），固定成本相对于很短的执行就显得很大。这个判断在原邮件里是定性的，没有比例数据；后来的证据也都是定性或单例的：2022 年他说简单查询的剖析里“能明显看到小块分配”，2023 年他给了一条最简单查询的 ExecutorState 统计（43784 字节、3 个块）。
  2. 原因一：工作放错了阶段。原文点名两类。
    • 创建 tupledesc。ExecInitResultTypeTL() 每次执行都由计划的目标列表重新建结果行描述（B3）。输入只有 Plan 里的 targetlist，同一个计划每次的结果都一样。
    • nodeAgg 初始化。ExecInitAgg() 对每个聚合查 pg_aggregate、确定转移函数和终结函数、准备函数调用信息，再把转移步骤编译成表达式（B3）。其中“查系统表、确定函数和类型”这部分，结果只取决于计划和系统表，与本次执行的参数和数据无关。
    对 prepared statement 来说，这些推导在每次 EXECUTE 时都要重复一遍，相当于把规划的一部分做了 N 次。
  3. 原因二：大量细小的分配。初始化时，每个节点、元组槽、ExprContext、ExprState、步骤数组、FmgrInfo、ScanKey、List 单元都是单独的 palloc。代价有三处：
    • 每次分配本身的开销：取整、查空闲链、写 chunk 头部（B5）；
    • 步骤数组从 16 起翻倍扩容，2021 年 Andres 说简单查询中这部分“相当显眼”；
    • 内存密度低：对象散落各处，执行时访问它们缓存命中差。
    收尾时上下文整体删除，首块之外的块要 free，下次执行再 malloc（B5）。上下文一旦长得比首块大，每次执行都会来回 malloc/free。2023 年 Jonah 报告的 FDW 场景就是这样：系统态 CPU 高，brk 调用多，调大初始块后吞吐几乎翻倍。

二、解决思路

按改动从小到大排列：

  1. 少分配，或者让分配更便宜。
    • 在表达式里记录步骤数，或者构建时先用 List、最后压成紧凑数组，避免步骤数组反复扩容（2021-11-04）；
    • 调大 CreateExecutorState 里硬编码的块大小，或者按已规划语句的复杂度决定 es_query_cxt 的块大小（2023-02-17）；
    • 提供“调用方承诺不单独释放”的分配接口：不走空闲链，不按 2 的幂取整，非断言构建可以不要 chunk 头部。整棵执行器状态树，很可能还有计划树，都适合这样分配（2023-02-20）。
  2. 一次分配到位（第 5、6 步）。先让节点瘦身，把大部分状态移进执行步骤（第 5 步）；再在 ExecInitNode() 之前加一遍处理，算出节点、元组槽、表达式上下文所需的全部内存，一次分配，ExecInitNode() 从中切分（第 6 步，表达式求值暂不纳入）。2023 年 Andres 仍把“至少把所有执行器节点本身放进一次分配”称为中长期目标。
  3. 把推导挪回规划期。这是问题 3 原文暗含的方向，例如让计划直接带上结果行描述或聚合的函数信息。原文和后续讨论都没有给出具体补丁。
  4. 根本不重复初始化。这就是问题 5 和第 7 步的方向：同一 prepared statement 的多次执行共享状态。见问题 5。

三、难点

  1. 哪些工作可以只做一次。权限要按执行时的用户检查；关系要在本事务中打开并加锁；运行时扫描键依赖参数；哈希表和排序缓冲依赖数据。只有“只由计划和系统表决定”的部分能挪走，挪走以后还要在系统表变化时跟着计划一起失效。（解读）
  2. 挪到规划期会让计划变大。缓存的计划本身已经很占内存。2019 年的 BUG #15923 里，报告者估算一条复杂视图查询的 prepared statement 约占 45MB（见问题 5 摘录）。在这一点上，问题 3 的“挪到规划期”和问题 5 的“降低内存”会互相牵制。（解读）
  3. 精确算出内存需求很难。第 6 步要求“先算账、再分配”的两遍处理，每种节点都要能报告自己需要多少内存。2019 年 Thomas Munro 质疑过这种两遍设计（针对紧凑复制计划树）：一串较小的块几乎一样好，只在最后一块浪费一点。另外，执行期还有“第二阶段”的分配（查询生命周期的元组等），扩展（FDW、CustomScan）也会在 es_query_cxt 里自行分配（Jonah 的场景），这些都没法事先算准。
  4. 分配器的约束。不单独释放的分配不能用 pfree，也不能用 repalloc、GetMemoryChunkSpace、GetMemoryChunkContext（David Rowley）。同一个上下文里，既有可以单独释放的分配，也有不可以的；单独开一个上下文又会多占内存（Andres）。调大默认块大小会让每个后端多占内存，而后端可能很多，David 提醒不能让后端的最坏情况变差。
  5. 不能拖慢用不上的场景。2022 年 Andres 对 Amit 补丁的意见是：即使新逻辑用不上，多出来的几次 makeNode、palloc0 和上下文创建，也落在“本来就是瓶颈”的启动路径上。任何预计算或复用机制，没有命中时多出的开销都要单独衡量。
  6. 先要有数据。2023 年 Andres 反复要求：执行器上下文在 ExecutorStart 结束和 ExecutorFinish 开始时的 MemoryContextStats、CPU 剖析、可复现的负载。他认为真正原因也可能是最大块大小，或者块大小爬升太慢，“没有数据之前不要钻得太深”。
  7. 改动面大。原型第一版试图一遍遍历计划树同时解决问题 1–4、不用现有初始化代码，作者的评价是“不是做不到，但非常非常笨重”。第二版只好复用现有初始化函数，问题 3 并没有触及。

（三）2019-10-23：表达式层的相对分配原型

译文这主要出于两个因素：a）表达式求值仍然常常占查询执行时间的很大一部分，开不开 JIT 都一样。b）目前 JIT 编译的查询无法缓存，因为生成的代码里含有每个查询都不同的指针。此外还有其他原因（例如使用更少内存、缩短初始化时间）。JIT 代码不够快、并且实际上无法缓存，主要原因是 ExprEvalStep 指向 LLVM“视野之外”的内存，例如经由 ExprEvalStep->resvalue 和各种 FunctionCallInfo。目前的做法是把原始指针值直接嵌入生成的程序（这实际上阻止了缓存）。LLVM 也不会真正透过这些内存引用做优化，它难以判断别名和生命周期。解决办法是把真正临时的东西改为在栈上分配，LLVM 能把它们转成 SSA 形式并正确优化。

译文5）在表达式初始化期间，以“相对”的方式计算分配。每项分配单独跟踪，主要由一个“偏移量”构成：偏移量从零开始，每分配一项就加上它的大小。对解释执行，这些分配所需的全部内存作为 ExprState 本身分配的一部分，紧跟在 steps[] 数组（现在也是内联的）之后；解释执行时访问它们，基本上就是把偏移量加到一个基址指针上。对 JIT 编译的执行，这些内存用 LLVM 的 alloca 指令分配，LLVM 可以把它优化成 SSA 形式（借助 Mem2Reg 或 SROA pass）。结合运算符内联，这能让 LLVM 把 PG 的函数调用完全优化掉，某些情况下甚至能做公共子表达式消除。

译文生成的代码还不能“完全”缓存：FunctionCallInfo->{flinfo, context} 仍然指向一个指针常量。我认为这可以用和其他部分相同的办法解决，只是我还没来得及做。

译文TPC-H Q01 的结果（单位毫秒）。branch=master/dev 为主线和补丁分支，jit=0/1 为是否开启 JIT，seq=0/1 为是否启用更快的顺序扫描顺序。作者说明这是规模因子 5、在笔记本上测的，“不宜太当真”。他的评价是“我认为相当不错”。

译文（John Naylor）这让我想起最近偶然看到的一个关于 prepared statement 内存管理的讨论串（即 BUG #15923 中 Andres 的回复）。我最近听说一种相对指针的技巧，可以在一次分配里实现树结构。如果 a 需要存储 b 相对于 a 的位置，就算 a = (char *) &b - (char *) &a；要找回 b，就算 (char *) &a + a。这个简单草图的一个问题是 0 会指向自己，而我们希望 0 仍然表示“无效指针”，这样 memset(0) 才能正确工作。以有符号单字节偏移为例，取值范围是 -128 到 127，可以把 -128 当作无效指针。要把原始的 0 解释为无效，需要一种编码，这里用异或即可：encode(-128) == 0，decode(0) == -128，于是 memset(0) 能正确工作，读出来就是无效值；同时仍然可以指向自己。这样就能存储 -127 到 127 之间的任何相对偏移，外加“无效偏移”，推广到更大的有符号整数类型也一样。我对解析树、计划树、执行树还不够熟悉，不知道这行不行得通，但也许值得在下个开发周期研究一下。

5.4　梳理

一、问题是什么

  1. 两种“内存开销”要分开看。
    • 每次执行的开销。每次 EXECUTE 都在新的 es_query_cxt 里建 PlanState、ExprState、元组槽等，结束时整体删除。原文“到处复制大量内存，从头初始化大量节点”说的是这一类。它既是 CPU 开销（与问题 3 重叠），也是内存的反复申请和释放。
    • 常驻开销。每个 prepared statement 的缓存计划（以及解析树）长期占着内存，每个后端各一份。2019 年的 BUG #15923 属于这一类：报告者的查询计划约 30MB（132 个节点），prepare 250 次后后端常驻内存约 7.35GB，他估算每条约 45MB；他最多保留 250 条，但连接池里有 10 个连接，服务器撑不住。
    原文的“在连续多次执行之间共享状态”针对的是前一类。后一类在 2019 年才被讨论，用到的技术（紧凑分配、一块内存加偏移量）与前一类相通。
  2. 为什么现在做不到共享。
    • 状态和一次执行绑定：PlanState、ExprState 都分配在本次执行的 es_query_cxt 里，执行结束整体删除（B2、B5）。
    • 不可变内容和可变内容混在一起：同一个 ExprEvalStep 里，既有每次都一样的操作码和常量，又有指向本次执行的结果格子、FunctionCallInfo 的指针（B4）。
    • 它们用绝对指针相连：复制一份就得修正所有内部指针（B7）；直接共享一份，又会在递归或交错执行时互相覆盖（B8）。
  3. “共享状态”具体指什么。（解读）
    • 可以共享：步骤操作码、常量、函数地址和类型信息、TupleDesc、扫描键模板、由计划决定的列号等；
    • 每次执行一份：元组槽的内容、resvalue/resnull 中间结果、FunctionCallInfo 的参数区、节点的运行计数、扫描位置、哈希表和排序状态，以及参数和快照的绑定。

二、解决思路

  1. 第 7 步：拆分加相对地址。把执行器节点和执行步骤的状态拆成可修改和不可修改两部分，尽量用相对地址代替绝对指针。这样执行器程序可以复用，也可以重入。受益者包括 prepared statement、plpgsql 和 JIT 代码生成。
  2. 克隆可写内存。可写部分如果只通过偏移量引用、内部没有绝对指针，就可以 memcpy 一份开始新一次执行，不可写部分原地共享（2018 年“内存密度”段，图 3、图 4 左）。
  3. 表达式层原型（2019-10，补丁 0026）。初始化时每项分配只记一个偏移，从 0 开始累加；解释执行时这些内存和 ExprState 一起分配，紧跟在内联的 steps[] 之后，访问时用基址加偏移；JIT 执行时改用 alloca 放在栈上，LLVM 可以把它优化成 SSA（图 2 右）。Andres 2021 年说明，更进一步的版本可以让 prepared statement 不必重建 ExprState，但需要更多数据改用相对指针。
  4. Robert 的折中（2021-11-05）。如果只为缓存 JIT，可以不用相对指针：把所有步骤和它们依赖的分配放进一个与 JIT 代码同生命周期的内存上下文；或者按类型各分配一个数组，照常用指针。Andres 的反驳见难点 1。
  5. 降低计划的常驻内存（2019-07）。Tom Lane 提出不支持单独释放、头部开销低的分配器，以及生成紧凑节点树的 copyObject 变体；Thomas Munro 提出“拉绳式”分配器和跨后端共享计划；Andres 提出把批量分配做成上下文选项、给节点树加“头”、在不可变的扁平树里用偏移量、写时复制加引用计数。
  6. 单实例加“正在使用”标记。（解读）plpgsql simple expression 在每个事务里只建一份 ExprState，求值期间标记为忙；遇到递归或上次出错，就走常规路径（B8、图 4 右）。这不是 Andres 提出的方案，却是 PostgreSQL 里现成的跨执行复用执行状态的做法，也接近 Robert 的同生命周期思路。

三、难点

  1. 可重入，这是核心难点。Andres 2021-11-05：“同一个表达式可能同时被求值多次，以递归的方式。所以你不能共享像 FunctionCallInfoData 这样的东西。”递归的 plpgsql 函数、同一 prepared statement 上交错读取的游标、查询里的函数再去执行同一份计划，都会让同一份状态在一次执行没结束时被再次使用。办法只有两种：每次执行一份可变区（Andres），或者只允许一处使用、其余回退（plpgsql）。后者还要处理执行中途出错留下的半成品状态。
  2. 指针遍布执行器。2021 年的原型清理到最后，表达式里仍剩 FunctionCallInfo->flinfo、->context，以及“表达式编译时”还不知道的 WindowFuncExprState->wfuncno。表达式之外，PlanState 的子节点、元组槽与 TupleDesc、ExprContext、结果关系信息等也都靠指针相连。全部改造，就是第 7 步的全部工作量。（后半句为解读）
  3. C 语言里的相对指针很难写好。Robert 评审说 RelFCIOff()、RelFCIIdx() 这类名字“几乎无法理解”；Andres 承认命名很烂，“如果这是 C++，很容易把相对指针包装得像普通指针”；他还说早期所有 Rel* 用同一个类型时很容易出错，编译器查不出来。Robert 希望复用已有的 utils/relptr.h，而补丁的 allocno 机制目前和它不兼容。
  4. 性能要权衡。Robert 担心 RELPTR_RESOLVE 在执行时解析的开销；Andres 回答在 x86 上就是基址加偏移，基址可以常驻寄存器，初步测试中内存密度提高的收益更大。这需要按负载重新验证。
  5. 不是所有东西都能 memcpy。buffer pin、打开的关系和索引扫描、tuplestore、哈希表、JIT 上下文这类资源有各自的登记和释放流程（ResourceOwner 等），复制内存并不能得到一份新的资源，每次执行仍须重新获取。（解读）
  6. 可复用程序的边界情况。2018 年计划的第 2、3 步提到，EXPLAIN ANALYZE 的插桩可能需要生成不同的程序，EvalPlanQual 也要单独一套程序。可复用的执行器程序同样要回答：插桩选项每次执行可能不同怎么办，EPQ 状态如何重置。Robert 在 2018 年还问过反向取数（backward fetch）如何支持。（第二句为解读）
  7. 工程规模和评审。2019 年的补丁集有 31 个补丁；Robert 指出需要更好的提交说明和注释；CommitFest 条目在 2020-09-30 被 Michael Paquier 标为 Returned with Feedback（理由是讨论串已经沉寂）；2021 年重整时 Andres 说 rebase “很痛苦”；2023 年 Daniel Gustafsson 接手分支，之后只拆出几项独立优化合入。

四、现状（截至 2026-11-13）

  • 第 7 步没有合入。表达式层原型在 GitHub 的 jit-relative-offsets 分支（最后提交 2021-11-04）和 dg-andres-relative-offsets 分支（2023-06-22 至 09-15 主要由 Daniel Gustafsson 提交，最后一次提交署名 Andres Freund）。没有找到后者对应的邮件讨论，完成度未核实。
  • 拆出来合入的独立优化：2742c45080（2020-02-24，减少聚合转移的步骤数）；d35d32d711、8dd7c7cd0a（2025-03-11，Daniel Gustafsson，strict 函数的快速路径、拆分 EEOP_DONE）。
  • src/backend/jit/README 的 Caching 一节（17.10 第 222–243 行，2026-11-13 的 master 相同）仍写着生成的代码含有每次执行内存的指针、不能缓存。
  • utils/relptr.h 在 17.10 中仍只有 freepage.c/freepage.h 使用。
  • 计划的常驻内存：PostgreSQL 16 起节点支持函数改为自动生成（964d01ae90，2022-07-09，Peter Eisentraut），Tom 说的“维护两份 copyfuncs.c”这个障碍已经不存在，但紧凑复制没有实现；PostgreSQL 17 的 bump 分配器也没有用于计划缓存。

2018-05-25 03:35 UTC Andres Freund Redesigning the executor (async, JIT, memory efficiency)

Message-ID: 20180525033538.6ypfwcqcxce6zkjj@alap3.anarazel.de

Hi,

The current executor structure limits us in a number of ways that are
becoming problematic.  I'll outline in this email how I think we should
rework it. Including a prototype for the first, most drastic, steps.

The primary problems with the current design that I want to address are:

1) Executor structure makes it hard to do asynchronous execution.  That
   comes into play in several cases. For example we want to be able to
   continue execution if no tuples are ready in one FDW below an append
   node, instead switch to another one. Similarly that could be relevant
   for parallel queries, with multiple gather nodes.

   A bit further out that'd also be very useful for continuing execution
   in a different part of the tree once blocked on IO. That'd e.g. be
   useful to build several hashtables for hashjoins at once.  There's
   some limitations of how we do IO for that atm however, it'd be easier
   to efficiently implement this if we had AIO support.

   With the current, tree-walking based architecture, it's hard to
   implement something like that, because we basically have to re-enter
   into the subtrees where we'd stopped. That'd requires adding new
   state-machine logic in every tree, including additional branches.

   What we basically need here is the ability to stop execution inside a
   specific executor node and have a multiplexer node (which can use
   WaitEventSets or such) decide which part of the execution tree to
   continue executing instead.

2) The tree-walking based approach makes it very hard to JIT compile the
   main portion of query execution without manually re-emitting all of
   executor/, which is obviously entirely unattractive.

   For the expression evaluation JIT the biggest benefit comes from
   removing the indirect branches between the expression steps and then,
   a close second, from having more efficient implementations of
   hot-path expression steps.

   That approach currently isn't feasible for the whole executor. The
   main sources for indirect branches / calls are ExecProcNode() and
   ExecEvalExpr() calls inside the the Exec*() nodes. To be able to make
   those constant we'd basically have to manually emit code for all of
   these (or attempt to rely on the inliner, but that doesn't work
   across deep, potentially self invoking, trees).  The expression code,
   which also used to be tree walking, avoids that now by having the
   indirect function calls nearly exclusively at the top-level.

Secondary issues that I also want to address, or at least get ready to
address, are:

3) Reduce the overhead of executor startup. In a number of workloads
   involving simple queries we currently spend most of the time within
   ExecInitNode().  There's two major problems here: For one a lot of
   work is done at executor initialization that should be part of
   planning (especially creating tupledescs and nodeAgg
   initialization). The other problem is that initialization does a lot
   of tiny allocations.

4) Make the executor faster, leaving JIT aside.

   Moving to a "push based" executor can yield noticable speedups: Right
   now returning a single tuple will often pass through a lot of
   indirect function calls (via ExecProcNode()).  By moving to a push
   based executor (where the first executed piece is reachable without
   any recursion), this can be significantly cheaper.  We also exercise
   the stack *a lot* right now, constantly pushing/poping stuff onto it
   that's not going to be used anytime soon.  Profiling shows that stack
   usage is quite a bottleneck right now.

5) Memory overhead of query execution.

   Right now executing a prepared statment has quite a massive memory
   overhead. We copy around a lot of memory, initialize a lot of nodes
   from scratch, etc. It'd be far better if we could share a lot of
   state between successive executions of the same prepared statement.

6) Plan ahead for vectorized / batched execution.

   Dealing with tuples one-by-one is inefficient from a cache locality,
   code locality and CPU pipelining perspective. Instead fully
   processing a single tuple from a page (evaluating qual, then joining
   it to other things etc), it's a lot more efficient to evaluate the
   qual for all the tuples on a page, and then pass all the matching
   tuples to the next execution step.

After playing with / pondering about various approaches, I think the
right way to approach this is to convert the tree-walk based execution
with a 'program' / bytecode interpreter based approach. Quite similar to
what we've done to expression evaluation in v10 (which then subsequently
was used to implement JIT compilation of expression evaluation in v11).

To address the memory density / startup overhead issue I think we need
to work towards two things: First, most of the memory needed for a query
should come from a single, accurately sized, allocation. Secondly, the
writable memory for query execution should be referenced using memory
offsets, rather than pointers. That way we can clone the writable memory
for query execution.

That's obviously quite a bit of a project.  Or rather projects.

I've started prototyping a solution for this.  The code for the
prototype is at
https://git.postgresql.org/gitweb/?p=users/andresfreund/postgres.git;a=tree;h=refs/heads/executor-rewrite;hb=refs/heads/executor-rewrite
(click on the repo to see the git url)
and I plan to continue working on that project in that git branch.

In my first iteration I'd tried to basically address 1-4 in a single
protytype, using a single pass over the plan tree, without using the
current executor initialization. Not impossible, but very very unwieldy.

In the second version of the prototype I'm instead only tackling 1-2,
and reuse the current executor node initialization functions. This
prototype adds support for generating and executing an opcode based
execution plan for a subset of query nodes (seqscan, index [only] scan,
hash / sort based aggregation without grouping sets, limit, inner
nestloop / hashjoin without batches) when the use_linearized_plan is set
and all nodes in the query are supported.

For example, this converts this converts TPCH's Q01:

tpch_1[26142][1]=# SET client_min_messages ='log';
tpch_1[26142][1]=# SELECT
	l_returnflag,
	l_linestatus,

	sum(l_extendedprice) AS sum_base_price,
	sum(l_extendedprice * (1 - l_discount)) AS sum_disc_price,

	avg(l_discount) AS avg_disc,

FROM
	lineitem
WHERE

into:

0: init_sort
1: seqscan_first
2: seqscan [j empty 5] > s0
3: qual [j fail 2] < scan s0
4: hashagg_tuple [j 2] < s0
5: drain_hashagg [j empty 7] > s1
6: sort_tuple [j 5] < s1
7: sort
8: drain_sort [j empty 10] > s2
9: return < s2 [next 8]
10: done

where s are numbered slots, j are, potentially conditional, jumps. This
works for a number of plans, but there's several where we currently bail
out.

The basic idea is to convert the current, largely unmodified, Plan tree
into a "linear" representation of steps that can be executed by an
interpreter similar to ExecInterpExpr().  Individual parts of a query
tree form "instructions" which together form a small program to execute
the query.  Obviously such a query will contain (conditional) backward
and forward jumps (which differentiates it from the expression case,
which knows only forward jumps).

This means that some of the current executor nodes get split into
multiple parts, because it's not permitted to recurse from within an
executor step.

A tuple can be returned to the user / caller by a special 'return tuple'
step. This just sets the "virtual" instruction pointer to the point
where execution should resume, allowing execution to continue at the
right spot when the next tuple is supposed to be returned (e.g. for
cursors). Instead of, as currently in the prototype, returning control
flow back to ExecutePlan() we could - and quite possibly should -
instead just process the tuple by having a 'send_slot' step or such.
But right now it's a good example how control flow can be interrupted at
any boundary.

For the async FDW (and gather, and IO, ...) cases, you'd have a
'scan_fdw' step that'd normally continue execution, but if there's no
tuple, it'd instead jump to a multiplexer step that'd use a WaitEventSet
to watch which of the to-be-waited-for FDWs is ready.

Despite being entirely unoptimized this already yields a measurable
speedup over the current executor for the TPCH queries it supports.

I think the big argument against this kind of project is that it's going
to be quite invasive. Not everything inside the executor will have to be
touched, but it's going to be a significant portion. But I don't think
there's really a way around that for the medium to long term future, and
I don't see how we'd gain anything by waiting further.

My (although I certainly hope/plan to not work on this alone) basic plan
to attack this is:

1) Expand prototype to cover all SELECT queries. That's mostly "just
   work". This'll reuse the current executor initialization with minimal
   modifications.

2) Reimplement EXPLAIN ANALYZE support. I'm not yet 100% sure what the
   best way to do so is - potentially it's just generating slightly
   different programs, where the steps contain additional code to
   perform the instrumentation.

3) Reimplement EvalPlanQual() infrastructure by generating a separate
   execution plan for EPQ, which replaces the relevant scan nodes with
   an execution step that return tuples from estate->es_epqTuple.  The
   current indirection / branches due to ExecScan() are fairly
   expensive.

4) Remove old executor *Exec() functions, and subsidiary code.

5) Clean up executor nodes, they should now require far less
   information, because a lot of the state will be in executor steps.

6) Introduce a new pass, run before ExecInitNode(), that accounts for
   all the necessary memory for, at least, nodes, slots, expression
   contexts.  Then convert ExecInitNode() to allocate from that.  I'd
   assume that we'd leave expression evaluation out of that, because
   such work would be a largely independent project.

7) Split state in the executor nodes / executor program steps into
   modifiable and non-modifiable parts, and store as much as reasonably
   possible using relative addresses rather than absolute pointers.
   That can then be used to make executor programs reusable and
   reentrant.  That's going to be useful for at least prepared
   statement, plpgsql and better JIT code generation.

8) Write a JIT implementation.

Thoughts?

Some of that is because this format is intrinsically hard to read, but

0: Initialize Sort (for step 7)

2: Iterate Seq Scan on linitem into slot 0
    If no more tuples, go to step 5.

    If no more tuples, go to step 7.

Even with this sort of TLC, I agree that reading this is no picnic,
but I think continuing to show the tree structure when the executing
plan has been linearized seems to have its own set of difficulties.
The way that time is reported today in EXPLAIN ANALYZE presumes that
execute recurses down the tree; that's how times for higher nodes end
up including times for subordinate nodes.  If we time each step
executed using this method, that will no longer be true.  We could
make it true.  For example we could make the Seq Scan time include
steps 1, 2, and 3, the Hash Aggregate on top of it include that time
plus steps 4 and 5, the Sort on top of that also include steps 0, 6,
7, and 8, etc.  But that sucks.  If we've got timing information for
each step individually, that's awesome, and power users are going to
want to see it.  One of the most common questions one has when looking
at today's EXPLAIN ANALYZE output is "where did the time go?" and we
want to provide the most accurate possible answer to that question.

Also, consider a plan that today looks like this:

Append
-> Seq Scan on p1
-> Seq Scan on p2
-> Seq Scan on p3

The linearized plan could omit the Append node altogether.  We just
went and made Append nodes have a cost because they do, but in cases
where the Append is neither parallel-aware nor the new async-capable
Append type we're presumably going to add nor doing partition pruning,
we can and probably should optimize it away completely.  That will
change which plan is fastest in some cases, I'm fairly sure.  It
doesn't keep you from reporting on the Append node as if it still
existed, but if you do, you're sorta lying.  Another case that I think
is kind of interesting is:

Nested Loop Semi Join
-> Seq Scan
-> Index Scan
    Index Cond: ...

If the index cond passes, we can emit the tuple returned by the Seq
Scan and jump back to fetch the next tuple from the Seq Scan.  Perhaps
the Nested Loop doesn't really exist at all.  If the join is something
other than a semi/anti join then you probably need the join to
project, unless all of the columns needed are from one side, but
that's all, unless the join itself has a Join Filter.  I think users
are going to want to see EXPLAIN ANALYZE output that makes it really
clear how the query has been optimized.  Sure, the existing format may
be easier for users in the short term, and certainly can be an option,
but seeing something that conceals rather than reveals how the
execution is really progressing may not be all that great in the end.

Maybe there are other ways of displaying the linearized plan that
would increase comprehensibility further.  For example, in your
version of the plan for TPC-H Q01, steps 0-1 are initialization, 2-4
are a loop, 5-6 are a loop, 7 is an independent step, 8-9 are another
loop, and 10 represents completion.  Maybe that can be used somehow to
make something easier to understand.  For example:

Initialize
-> Initialize Sort 1
-> Initiialize Seq Scan on lineitem
Loop
-> Iterate Seq Scan on lineitem
    Break if no more tuples
-> Continue if ...
-> Load Into Hash Aggregate 1
Loop
-> Fetch From Hash Aggregate 1
-> Load Into Sort 1
Perform Sort 1
Loop
-> Fetch from Sort 1
-> Return Tuple

Maybe that doesn't seem that much easier, but at least it doesn't
involve needing to understand step numbers.  It strikes me that this
kind of organization could potentially also be useful for a query
progress indicator.  If the whole plan is a series of loops and other
steps, you can say things like -- well, the steps we've already
completed represent 30% of the estimated cost.  The steps we haven't
started yet represent another 30% of the estimated cost.  So we're
somewhere between 30% done and 70% done.  And then we can guess what
fraction of the iterations we've completed for the loop we're
currently performing.  Obviously this is all pie-in-the-sky, but it
certainly seems like this kind of thing would enable estimation that
we can't easily perform today.

> (click on the repo to see the git url)
> and I plan to continue working on that project in that git branch.

> 
> In my first iteration I'd tried to basically address 1-4 in a single
> protytype, using a single pass over the plan tree, without using the
> current executor initialization. Not impossible, but very very unwieldy.
>

> and reuse the current executor node initialization functions. This
> prototype adds support for generating and executing an opcode based
> execution plan for a subset of query nodes (seqscan, index [only] scan,
> hash / sort based aggregation without grouping sets, limit, inner
> nestloop / hashjoin without batches) when the use_linearized_plan is set
> and all nodes in the query are supported.
>

>

> 	sum(l_extendedprice * (1 - l_discount) * (1 + l_tax)) AS sum_charge,
> 	avg(l_quantity) AS avg_qty,
> 	avg(l_extendedprice) AS avg_price,
> 	avg(l_discount) AS avg_disc,
> 	count(*) AS count_order
> FROM
> 	lineitem
> WHERE
> 	l_shipdate <= date '1998-12-01' - interval '74 days'

> 	l_returnflag,
> 	l_linestatus
> ORDER BY
> 	l_returnflag,
> 	l_linestatus;

>

> 
> 0: init_sort
> 1: seqscan_first
> 2: seqscan [j empty 5] > s0
> 3: qual [j fail 2] < scan s0
> 4: hashagg_tuple [j 2] < s0
> 5: drain_hashagg [j empty 7] > s1
> 6: sort_tuple [j 5] < s1
> 7: sort
> 8: drain_sort [j empty 10] > s2
> 9: return < s2 [next 8]
> 10: done
> 
> where s are numbered slots, j are, potentially conditional, jumps. This
> works for a number of plans, but there's several where we currently bail
> out.
> 
> The basic idea is to convert the current, largely unmodified, Plan tree
> into a "linear" representation of steps that can be executed by an
> interpreter similar to ExecInterpExpr().  Individual parts of a query
> tree form "instructions" which together form a small program to execute
> the query.  Obviously such a query will contain (conditional) backward
> and forward jumps (which differentiates it from the expression case,
> which knows only forward jumps).
> 
> This means that some of the current executor nodes get split into
> multiple parts, because it's not permitted to recurse from within an
> executor step.
>

> step. This just sets the "virtual" instruction pointer to the point
> where execution should resume, allowing execution to continue at the
> right spot when the next tuple is supposed to be returned (e.g. for
> cursors). Instead of, as currently in the prototype, returning control
> flow back to ExecutePlan() we could - and quite possibly should -
> instead just process the tuple by having a 'send_slot' step or such.
> But right now it's a good example how control flow can be interrupted at
> any boundary.
>

> 'scan_fdw' step that'd normally continue execution, but if there's no
> tuple, it'd instead jump to a multiplexer step that'd use a WaitEventSet
> to watch which of the to-be-waited-for FDWs is ready.

nodes conducts execution, not only by FDW nodes but all source
nodes including local scans, I suppose.

> to be quite invasive. Not everything inside the executor will have to be

> there's really a way around that for the medium to long term future, and
> I don't see how we'd gain anything by waiting further.

>    expensive.
>

>

>

>    all the necessary memory for, at least, nodes, slots, expression
>    contexts.  Then convert ExecInitNode() to allocate from that.  I'd
>    assume that we'd leave expression evaluation out of that, because
>    such work would be a largely independent project.

>    modifiable and non-modifiable parts, and store as much as reasonably
>    possible using relative addresses rather than absolute pointers.
>    That can then be used to make executor programs reusable and

FWIW, I've thought for some time that we should invent a memory context
allocator that's meant for data that doesn't get realloc'd (much) after
first allocation, with lower overhead than aset.c has.  Such an allocator
would be ideal for plancache.c, and perhaps other use-cases such as
plpgsql function parsetrees.  IMV this would have these properties:

* Doesn't support retail pfree; to recover space you must destroy the
whole context.  We could just make pfree a no-op.  With the details
sketched below, repalloc would have to throw an error (because it would
not know the size of the old chunk), but I think that's OK for the
intended purpose.

* Minimum chunk header overhead, ie only the context pointer required by
the mmgr.c infrastructure.  In particular, don't store the chunk size.

* Request sizes are only rounded up to a MAXALIGN boundary, not to a
power of 2.

* All else could be pretty much the same as aset.c, except we'd not need
to have any freelist management.  I would imagine that callers might want
to use a smaller initial and maximum block size than is typical with
aset.c, to reduce end-of-context wastage, but that would be up to the
callers.  (Possibly, instead of freelists, we'd trouble to track
end-of-block space in more than one active block, so that we avoid
wasting such space when a large allocation doesn't quite fit.)

This wouldn't take very much new code, and it would potentially offer
up to perhaps 2X space savings compared to aset.c, thanks to cutting the
per-chunk overhead.  Whether that's enough to float your boat with respect
to cached plans isn't too clear, though.

A totally different idea is to make a variant version of copyObject
that is intended to produce a compact form of a node tree, and does
not create a separate palloc allocation for each node but just packs
them as tightly as it can in larger palloc chunks.  This could outperform
the no-pfree-context idea because it wouldn't need even context-pointer
overhead for each node.  (This relies on node trees being read-only to
whatever code is looking at them, which should be OK for finished plan
trees that are copied into the plancache; otherwise somebody might think
they could apply repalloc, GetMemoryChunkContext, etc to the nodes,
which'd crash.)  The stumbling block here is that nobody is gonna
tolerate maintaining two versions of copyfuncs.c, so you'd have to
find a way for a single set of copy functions to support this output
format as well as the traditional one.  (Alternatively, maybe we
could learn to autogenerate the copy functions from annotated struct
definitions; people have muttered about that for years but not done
anything.)

Or you could imagine flattening the node tree into serialized text
(cf outfuncs.c/readfuncs.c) and compressing that, although I fear that
the overhead of doing so and recovering a node tree later would be
excessive.  Also, the serialized-text representation tends to be pretty
bulky, and I don't know if compression would win back enough to make it
all that much smaller than the existing in-memory representation.

Hi,

TL;DR: Some performance figures at the end. Lots of details before.

For a while I've been on and off (unfortunately more the latter), been
hacking on improving expression evaluation further.

This is motivated by mainly two factors:
a) Expression evaluation is still often a very significant fraction of
   query execution time. Both with and without jit enabled.
b) Currently caching for JITed queries is not possible, as the generated
   queries contain pointers that change from query to query

but there are others too (e.g. using less memory, reducing
initialization time).

The main reason why the JITed code is not faster, and why it cannot
really be cached, is that ExprEvalStep's point to memory that's
"outside" of LLVMs view, e.g. via ExprEvalStep->resvalue and the various
FunctionCallInfos. That's currently done by just embedding the raw
pointer value in the generated program (which effectively prevents
caching). LLVM will not really optimize through these memory references,
having difficulty determining aliasing and lifetimes.  The fix for that
is to move for on-stack allocations for actually temporary stuff, llvm
can convert that into SSA form, and optimize properly.

In the attached *prototype* patch series there's a lot of incremental
improvements (and some cleanups) (in time, not importance order):

1) A GUC that enables iterating in reverse order over items on a page
   during sequential scans. This is mainly to make profiles easier to
   read, as the cache misses are otherwise swamping out other effects.

2) A number of optimizations of specific expression evaluation steps:
   - reducing the number of aggregate transition steps by "merging"
     EEOP_AGG_INIT_TRANS, EEOP_AGG_STRICT_TRANS_CHECK with EEOP_AGG_PLAIN_TRANS{_BYVAL,}
     into special case versions for each combination.
   - introducing special-case expression steps for common combinations
     of steps (EEOP_FUNCEXPR_STRICT_1, EEOP_FUNCEXPR_STRICT_2,
     EEOP_AGG_STRICT_INPUT_CHECK_ARGS_1, EEOP_DONE_NO_RETURN).

3) Use NullableDatum for slots and expression evaluation.

   This is a small performance win for expression evaluation, and
   reduces the number of pointers for each step. The latter is important
   for later steps.

4) out-of-line int/float error functions

   Right now we have numerous copies of float/int/... error handling
   elog()s. That's unnecessary. Instead add functions that issue the
   error, not allowing them to be inlined. This is a small win without
   jit, and a bigger win with.

5) During expression initialization, compute allocations to be in a
   "relative" manner. Each allocation is tracked separately, and
   primarily consists out of an 'offset' that initially starts out at
   zero, and is increased by the size of each allocation.

   For interpreted evaluation, all the memory for these different
   allocations is allocated as part of the allocation of the ExprState
   itself, following the steps[] array (which now is also
   inline). During interpretation it is accessed by basically adding the
   offset to a base pointer.

   For JIT compiled interpetation the memory is allocated using LLVM's
   alloca instruction, which llvm can optimize into SSA form (using the
   Mem2Reg or SROA passes). In combination with operator inlining that
   enables LLVM to optimize PG function calls away entirely, even
   performing common subexpression elimination in some cases.

There's also a few changes that are mainly done as prerequisites:
A) expression eval: Decouple PARAM_CALLBACK interface more strongly from execExpr.c
   otherwise too many implementation details are exposed

B) expression eval: Improve ArrayCoerce evaluation implementation.

   the recursive evaluation with memory from both the outer and inner
   expression step being referenced at the same time makes improvements
   harder. And it's not particularly fast either.

C) executor: Move per-call information for aggregates out of AggState.

   Right now AggState has elements that we set for each transition
   function invocation. That's not particularly fast, requires more
   bookkeeping, and is harder for compilers to optimize. Instead
   introduce a new AggStatePerCallContext that's passed for each
   transition invocation via FunctionCallInfo->context.

D) Add "builder" state objects for ExecInitExpr() and
   llvm_compile_expr(). That makes it easier to pass more state around,
   and have different representations for the expression currently being
   built, and once ready. Also makes it more realistic to break up
   llvm_compile_expr() into smaller functions.

E) Improving the naming of JITed basic blocks, including the textual
   ExprEvalOp value. Makes it a lot easier to understand the generated
   code.  Should be used to add a function for some minimal printing of
   ExprStates.

F) Add minimal (and very hacky) DWARF output for the JITed
   programs. That's useful for debugging, but more importantly makes it
   a lot easier to interpret perf profiles.

The patchset leaves a lot of further optimization potential for better
code generation on the floor, but this seems a good enough intermediate
point.  The generated code is not *quite* cachable yet,
FunctionCallInfo->{flinfo, context} still point to a pointer constant. I
think this can be solved in the same way as the rest, I just didn't get
to it yet.

Executing generic plans involving partitions is known to become slower
as partition count grows due to a number of bottlenecks, with
AcquireExecutorLocks() showing at the top in profiles.

Previous attempt at solving that problem was by David Rowley [1],
where he proposed delaying locking of *all* partitions appearing under
an Append/MergeAppend until "initial" pruning is done during the
executor initialization phase.  A problem with that approach that he
has described in [2] is that leaving partitions unlocked can lead to
race conditions where the Plan node belonging to a partition can be
invalidated when a concurrent session successfully alters the
partition between AcquireExecutorLocks() saying the plan is okay to
execute and then actually executing it.

However, using an idea that Robert suggested to me off-list a little
while back, it seems possible to determine the set of partitions that
we can safely skip locking.  The idea is to look at the "initial" or
"pre-execution" pruning instructions contained in a given Append or
MergeAppend node when AcquireExecutorLocks() is collecting the
relations to lock and consider relations from only those sub-nodes
that survive performing those instructions.   I've attempted
implementing that idea in the attached patch.

Note that "initial" pruning steps are now performed twice when
executing generic plans: once in AcquireExecutorLocks() to find
partitions to be locked, and a 2nd time in ExecInit[Merge]Append() to
determine the set of partition sub-nodes to be initialized for
execution, though I wasn't able to come up with a good idea to avoid
this duplication.

I recently heard of a technique for relative pointers that could enable
tree structures within a single allocation.

If "a" needs to store the location of "b" relative to "a", it would be
calculated like

a = (char *) &b - (char *) &a;

...then to find b again, do

typeof_b* b_ptr;
b_ptr = (typeof_b* ) ((char *) &a + a);

One issue with this naive sketch is that zero would point to one's self,
and it would be better if zero still meant "invalid pointer" so that
memset(0) does the right thing.

Using signed byte-sized offsets as an example, the range is -128 to 127, so
we can call -128 the invalid pointer, or in binary 0b1000_0000.

To interpret a raw zero as invalid, we need an encoding, and here we can
just XOR it:

#define Encode(a) a^0b1000_0000;
#define Decode(a) a^0b1000_0000;

Then, encode(-128) == 0 and decode(0) == -128, and memset(0) will do the
right thing and that value will be decoded as invalid.

Conversely, this preserves the ability to point to self, if needed:

encode(0) == -128 and decode(-128) == 0

...so we can store any relative offset in the range -127..127, as well as
"invalid offset". This extends to larger signed integer types in the
obvious way.

Putting the above two calculations together, the math ends up like this,
which can be put into macros:

absolute to relative:
a = Encode((int32) (char *) &b - (char *) &a);

relative to absolute:
typeof_b* b_ptr;
b_ptr = (typeof_b* ) ((char *) &a + Decode(a));

I'm not yet familiar enough with parse/plan/execute trees to know if this
would work or not, but that might be a good thing to look into next cycle.
